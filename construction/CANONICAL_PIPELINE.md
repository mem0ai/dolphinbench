# Canonical DolphinBench Construction Pipeline

This is the only supported way to create a later DolphinBench quarter. It has two
stages:

1. `construction.plan_quarter_events` creates a candidate quarter plan. A
   human must inspect and accept that plan.
2. `construction.quarter_runner` executes the accepted plan week by week,
   starting from an accepted `*_final` checkpoint.

Do not use any other planner, schedule generator, writer, or repair pipeline
to create a new quarter.

## Stage 1: Create And Accept The Quarter Plan

The quarter-plan command receives the long-range overview, the previous
quarter plan, the current checkpoint, the persona context, and the exact
quarter dates. It proposes the developments and facts for the new quarter.
It does not create sessions or change the accepted corpus.

If the starting checkpoint already covers part of that calendar quarter, the
planner reads its `accepted_through` date and may create events only from the
following day through the quarter end. It receives the accepted messages from
the month immediately before that first new date. Deterministic validation
rejects any proposed event that overlaps the accepted history.

Run it with:

```bash
python -m construction.plan_quarter_events \
  --persona <persona> \
  --persona-sheet <persona-sheet.md> \
  --generator-context <generator-context.md> \
  --overview <overview.json> \
  --starting-checkpoint <previous-quarter-final-checkpoint> \
  --previous-quarter-plan <previous-accepted-quarter-plan.json> \
  --period-start <YYYY-MM-DD> \
  --period-end <YYYY-MM-DD> \
  --output <quarter-plan-run-directory> \
  --confirm-paid-call
```

The command must pass validation and produce
`candidate_quarter_plan.json`. The candidate is not accepted merely because
the command succeeded. A human reviews the proposed developments, entities,
facts, dates, replacements, and continuity. Only after that review is the
candidate copied to the active accepted quarter-plan path, for example:

```bash
cp <quarter-plan-run-directory>/candidate_quarter_plan.json \
  construction/v2/<persona>/plans/quarters/<YYYY>_q<1-4>.json
```

The accepted quarter plan has exactly these top-level fields:
`period_start`, `period_end`, `protected_changes`, `new_entities`, and
`events`. It contains no weekly schedule, weekly brief, or ordinary
same-week occurrence list. The weekly planner creates those ordinary
occurrences while it writes each week.

The quarter planner may introduce a new person, company, account, product,
project, or place when a concrete event depends on identifying it and no
accepted entity represents the same thing. The multi-year overview does not
need to pre-name every such entity. New entities must have a concrete role and
must first appear in their stated introduction event. Do not add names merely
as background or decoration.

When an accepted event establishes lasting terms, both the event and its fact
must state every exact date, amount, limit, owner, scope, and condition that
could change a later action. A vague phrase such as "agreed terms" cannot stand
in for exact terms that the history established.

The accepted plan must then be referenced by a complete config containing the
exact eleven keys documented in [`v2/README.md`](v2/README.md). The config is
the explicit record of the accepted quarter inputs; it is not generated by
the weekly runner.

## Stage 2: Execute The Accepted Quarter

Run the quarter only after the plan is accepted and the starting checkpoint is
an authenticated `*_final` checkpoint:

```bash
python -m construction.quarter_runner \
  --config <accepted-quarter-config.yaml> \
  --out <new-quarter-run-directory> \
  --tool-python <path-to-tool-python> \
  --confirm-paid-calls
```

The runner:

- starts on the day after the accepted checkpoint;
- divides the remaining quarter into contiguous seven-day windows;
- first supplies a story call with the complete accepted developments that must
  finish during those dates. An accepted development that has started but
  finishes later includes its full what_happens, identity, dates, subjects, and
  eventual outcome so the current week remains consistent without turning
  intermediate steps into required contacts. The call also receives readable current
  conditions, known people and other named subjects,
  a short summary of each unfinished matter, calendar events that overlap those
  dates or may be changed by a request made during those dates, human-readable
  names and basic identifying metadata for other existing
  app items, and earlier situations grouped chronologically by week. The story
  call does not receive duplicate messages from unfinished matters, app-item
  body text, internal record IDs, tool schemas, tool arguments, or fact IDs;
- supplies every accepted future restriction from the quarter plan whose date
  is after the current week, so an ordinary weekly contact cannot assign or
  complete that later result early;
- asks that story call for the complete week in an active assistant relationship
  and every contact that naturally follows from the events of those dates. A
  complete seven-day window must contain twenty-three to twenty-four contacts, and
  the runner checks that count before making the exact-planning call. Every
  contact must have a real separate reason. The call must not create density by
  splitting one situation, inventing minor problems, or adding success reports;
- supplies a short record of every accepted contact in the current quarter and
  the thirteen weeks before that quarter began, while preserving the preceding
  fourteen days in greater detail;
- supplies the latest accepted user messages from the same unfinished matter to
  the exact planner and writer when a fixed contact continues it, so those steps
  can preserve continuity without repeating an explanation, role, boundary, or
  instruction that is already established;
- calls GPT-5.6 Sol once to fix what happens and every natural contact;
- replaces that call's response-local contact labels with unique IDs derived
  from the persona, contact date, and order, including every within-week
  reference to an earlier contact;
- calls GPT-5.6 Sol once more with those fixed contacts, every accepted fact that
  is still current, app records, and simulated tools. This call checks every
  fixed contact against those facts and checks that its dates do not describe a
  future time as past or violate a stated time limit before adding fact links,
  continuing-state changes, and exact app operations. It also receives the complete
  current contents of every calendar event already selected for the week. Code
  stops before writing or replay if an event update was planned without the
  event's complete current body in that call. The second call may add only fact links,
  continuing-state changes, and exact app operations. Code rejects any added,
  missing, reordered, or changed contact;
- validates the weekly plan and tool arguments with deterministic code;
- assigns the final session IDs and executes the planned operations on a copy of
  the app state before calling the writer; any failed operation stops the week;
- gives each writer contact its fixed plan, fixed app operations, and only the
  results of operations that happened before that contact;
- calls GPT-5.6 Sol at medium reasoning once to write only the user messages; it cannot add or
  change app operations;
- validates the messages, then reuses the already-executed operations, results,
  app changes, and projected app state when building the checkpoint;
- saves the final user-visible message text as the accepted description of each
  session for future planning. The earlier private story description remains a
  run record and never becomes future history context;
- chains each validated candidate checkpoint into the next window;
- calls GPT-5.6 Sol once after the complete quarter to review all generated
  sessions together for contradictions, unexplained changes, repetition, and
  unclear writing, including messages that disagree with their recorded app
  actions. The input groups the sessions by their exact generated week and
  includes the exact runtime contract for every simulated tool used in the
  quarter. The response must account for every week and separately identify
  findings that require comparing more than one week; and
- writes the quarter's final checkpoint only after every window and the final
  review pass.

The program saves each structured weekly request as JSON, but renders it as
labeled plain text for the model. The weekly writer may report that an ordinary
planned contact conflicts with a supplied current fact. Any such report stops
the week; the system does not hide, omit, or automatically repair the conflict.

The weekly planner sees `current_ordinary_states` reconstructed from accepted
`session_purposes`. These are continuing ordinary conditions or terms, such as
a current schedule, home condition, commercial quantity, or unresolved claim.
They are not benchmark facts or reasons to invent a contact. The planner records
a changed continuing condition in `current_state_changes` using the same stable
key; the latest value replaces the earlier value and does not expire.
Closing the unfinished conversation in which a condition was first recorded
does not itself change that condition. The planner updates it only when the
fixed weekly story explicitly states what changed.
When a named inventory, list, or rollout has a current count or status that a
later contact will revisit, the planner may preserve that count or status in
the same mechanism. It must not create state rows for every named object or
completed task.

The weekly planner owns both the requested assistant result and every simulated
app operation. An operation may use a value supplied by a current fact or app
record, but it must not add a new instruction, recipient, condition, assignment,
or content that the current contact did not request or establish. This is a
semantic planning rule, not a literal text-matching rule; the final quarter
review checks the completed contact and operation together.

The exact app-action planner receives a compact index of all visible app records.
It receives full original contents only for a record explicitly named in a fixed
contact or explicitly linked as an earlier accepted app item. The complete original
records remain available to deterministic validation and replay. If a fixed contact
contradicts a supplied current fact or exact app record, the planner reports
`factual_problem`; the existing bounded contact correction may repair that contact
and its source material once. The exact planner also receives accepted outcomes in
or after the window and completed accepted contacts that share a fixed contact's
subject IDs; the bounded correction receives that same contact-specific evidence
when needed to repair a reported conflict. An impossible-action correction must preserve source
material, and a second failure stops the week.

A recurring activity may reappear, but a new date alone does not justify
another assistant contact. A new contact needs a changed circumstance or other
real need. Do not repeat an unchanged medical rule, safety boundary, ownership
split, or disclaimer unless the current action would be wrong without that
exact term. Keep exact terms when they are needed.

`update_doc` replaces a document by default. The planner may append only when
the new text is additional history and every existing statement remains true.
If an update makes an old status, plan, dimension, owner, decision, or open item
false, the planner must replace the document with one complete corrected body.
It must not create a substitute document when the requested existing record is
not visible in the app records or earlier same-week results. When any planned
external action cannot be performed with the supplied tools and records, the
app-operation planner reports the exact missing tool, argument, or record. The
story planner then receives only the affected contact and that reason. It may
change only the requested assistant action and the minimum wording needed to
make the revised request clear. It cannot change the date, people, real-world
situation, source material, accepted developments, facts, or unfinished-work
state. The app-operation planner processes that corrected contact once. If the
action is still impossible, the week stops.

For `send_email`, `to` identifies one recipient. When the same email has several
recipients, the planner puts one person in `to` and the others in `cc`; it never
combines several identities into the `to` string.

`create_calendar_event` rejects a new event only when an existing event has the
same start and end and at least one attendee in common. Partial overlaps and
same-time events with no shared attendee remain valid.

For an accepted development that spans more than one week, the planner may show
intermediate progress before the end date. The lasting facts declared by that
development are supplied only in the week when the development ends, and local
validation rejects a plan that establishes them earlier.

The preceding fourteen days preserve concrete details and any exact source
material that the user supplied. Earlier contacts from the current quarter and
the thirteen weeks before it began are short records used to prevent repetition
and unexplained changes. A simulated tool is offered to the planner only when it
is approved for history generation and, when the tool reads an existing record,
the current app state contains a record it can actually return.

`continues_from` means a direct continuation of earlier unfinished work. A
continuation must copy that work's exact `thread_id`; deterministic validation
rejects another spelling or replacement ID. When the continuation finishes the
work, checkpoint construction removes the referenced unfinished item.

`uses_items_created_by_contact_ids` is separate from unfinished work. A story
contact uses it only when the requested app action needs a document, event, or
other app item created by an earlier contact in the same generated week. The
app planner must use the corresponding earlier operation result, and validation
requires the declared contact IDs and the actual operation references to match.
This field does not open or continue a thread.

If the command stops, run the same command again with the same config and
output directory. The runner authenticates the completed weekly checkpoint
chain, reuses that unbroken prefix, and continues at the first unfinished
week. It refuses a changed config, a broken checkpoint chain, or an already
completed quarter.

To inspect only the story for the next unfinished week, add
`--stop-after-story`. The runner makes only that story call, writes no app
operations, messages, or checkpoint, and pauses on the same week. Rerun the
same command and output directory without `--stop-after-story` to reuse the
saved story and complete that week through the normal canonical path.

The quarter planner has the same behavior for an incomplete output directory:
rerunning the same command checks each stage in order. A stage with a saved
response is completed: its saved request and prompt must exist and match the
current inputs exactly before the response is reused. A stage with no response
is unexecuted: if both its request and prompt exist, the command replaces them
with the current inputs and runs that stage; if only one exists, it refuses the
malformed record. It then starts at the first missing response, including a
fact repair or the review after a fact repair when those stages are reached.

The quality review request contains one copy of the proposed events, one copy
of the current facts, event-level IDs for selected supporting facts and source
sessions, the recent session purposes, only the accepted messages named by
those source-session IDs, and one copy of the replacement descriptions. It
does not contain a repeated fact-check object or a second copy of the story.
After a fact repair, the next review contains only the repaired events and
their evidence. Its rows replace all older review rows for those events, so
stale fact keys cannot remain in the saved review and rows for other events
keep their order. The planner may make one correction during a new planning
run. If the completed run still fails, do not correct that directory again.
Use the failed candidate as the source for a new correction run.

Every run that reaches a complete quarter review also writes the current
combined state at its root: `consolidated_story_response.json`,
`consolidated_fact_finalization_response.json`,
`candidate_replacement_accounting.json`, `candidate_quarter_plan.json`, and
`consolidated_quality_review_response.json`. The ordinary stage request and
response files remain raw call records for provenance and resumption.

To correct a failed candidate, use the same command with
`--source-candidate <failed-run>` and a new `--output <new-run>`. The command
rebuilds the current plan from the saved candidate and its last complete review
request. It refuses to continue unless the rebuilt plan exactly matches the
saved candidate. By default, it repairs only rows that failed the saved
automatic review.

When a complete approved audit found additional defects, pass
`--human-review-findings <approved-findings.json>` with the failed source. The
file is a JSON object with exactly one `findings` list. Each finding has a
nonempty `reason` and exactly one of these shapes:

```json
{
  "findings": [
    {"event_id": "event-id", "reason": "What must change."},
    {
      "event_id": "event-id",
      "replacement_event_id": "new-event-id",
      "reason": "Rename this event and update later references."
    },
    {
      "event_id": "event-id",
      "fact_key": "fact-key",
      "reason": "What the proposed fact must change or preserve."
    },
    {
      "event_id": "event-id",
      "fact_key": "fact-key",
      "replaced_fact_ref": "id:123",
      "reason": "What this replacement record must change or preserve."
    }
  ]
}
```

The command merges approved findings with the saved automatic failures before
repair. It rejects unknown event IDs, unknown fact keys, replacement references
not used by that fact, blank reasons, duplicate targets, empty lists, and extra
fields. An approved event-ID rename is the only way a correction may change an
event ID. Code updates every later `builds_on_event_ids` reference, fact
annotation event ID, and same-quarter replacement reference before fact repair.
The command copies the approved findings file into the new output as
`approved_correction_findings.json` and records its SHA-256 hash in
`failed_candidate_source.json`; a rerun refuses a changed or missing copy.

The command sends failed event rows to event repair and failed fact or
replacement rows to fact repair. Fact repair may also correct the numeric
earlier-fact links for those failed events when the review shows that a fact
used or carried forward earlier information without naming its source. It
cannot change links or facts for any other event. After repair, code compares
the corrected plan with the failed plan. The saved model results are kept for
every byte-identical event, fact, and replacement relationship. One model
review checks only changed objects and replacement relationships directly
affected by those changes. Deterministic validation still checks the complete
corrected plan. The source directory is never changed. Rerunning the new
output reuses its saved calls.

When a failed event genuinely needs to identify a new entity, event repair
receives the accepted entity names and roles and may add the needed entity.
Its stated introduction event must be one of the repaired events and must be
that entity's first appearance. Later repaired events may use the same entity.

A passed candidate is complete and cannot be rerun in place. To correct a
passed but not-yet-accepted candidate after a human inspection, use the same
planner with a new output directory, the passed candidate as
`--source-candidate`, and a saved `--human-review-findings` file. Each finding
names one event, one proposed fact, the exact `id:<number>` or
`key:<fact-key>` it replaces, and the human's concrete reason. The planner
calls only the existing fact-repair and quality-review stages, writes a new
candidate, and leaves the original candidate unchanged as provenance.

There is no separate quarter schedule, contact scheduler, weekly LLM review,
or general repair loop in this execution path. The only automatic correction
changes one planned assistant request when the supplied tools or records cannot
perform it, and it runs at most once for that contact. The one quarter-wide
history review is part of `quarter_runner` and runs only after all weekly windows pass.
`construction.build_history_window` and `construction.history_quarter_review`
are internal implementations used by `quarter_runner`; neither is a separate
user-facing generation command.

### Correct A Failed Whole-Quarter Review

When every weekly window passed but the one whole-quarter review failed, an
operator may make an explicitly approved, narrow correction without rerunning
weekly model calls:

```bash
python -m construction.quarter_runner \
  --config <accepted-quarter-config.yaml> \
  --out <new-correction-run-directory> \
  --tool-python <path-to-tool-python> \
  --source-failed-quarter <failed-quarter-run-directory> \
  --approved-history-corrections <approved-corrections.json> \
  --confirm-paid-calls
```

Both correction arguments are required together. The output directory must be
new. The runner authenticates that the source failed specifically at
`history_quarter_review`, that every configured weekly window passed, that its
config and checkpoint chain match, and that the source has no final checkpoint.
It never changes the source.

A failed review may identify only some instances of a repeated problem. Before
writing the correction file, inspect the entire generated quarter for every
session that uses the same term, app record, thread, recurring situation, or
dependent fact. Compare exact dates, times, quantities, and units with the
accepted quarter plan. When a correction changes any of those values, inspect
every later message, fact, and app operation that refers to it. Put the complete
set of related replacements and removals in one correction file; do not rerun
the paid review after fixing only the session IDs named in one finding.

The correction file is a plain JSON object with exactly `replacements` and
`removals`. A replacement has `session_id`, `messages`, `purpose`, and
`app_operations`, and may include `current_state_changes`, `new_facts`, and
`what_remains_after_contact`. The last field may replace the nonempty remainder
of an already-open thread; it cannot open or close a thread.
Replacement `new_facts` may correct only statement text on facts created by
that same source session. The replacement must preserve the source fact count
and order, and every fact must exactly preserve `key`, `applies_when`,
`subjects`, `supersedes`, and `evidence_contact_ids`; only a nonempty
`statement` may differ. Additions, removals, reordering, and metadata changes
are rejected. During replay, the validated replacement facts replace the
source session's fact declarations so their numeric fact IDs remain stable. A
replacement without `new_facts` keeps the source facts, so legacy correction
files remain valid. Each ordinary-state change has `key`, `subject_ids`, and
`statement`. Its subjects must be accepted entities and its statement must
appear verbatim in the corrected user messages. During replay, a supplied
replacement state list replaces the source session's ordinary-state changes. A
replacement otherwise keeps the source state list. Replacements change only
those fields on an existing quarter session.
Removals name existing quarter session IDs. Duplicate IDs, unknown or
outside-quarter sessions, malformed operations, overlapping replacement and
removal IDs, and removals that discard durable facts or introduced entities are
rejected.

Thread removals are normally rejected. A complete self-contained thread may be
removed only when every session in that thread is removed, no retained session
references any removed session, contact, or thread, and none of the removed
sessions establishes facts or entities. A removed complete thread may also
discard temporary `current_state_changes`, but only when each removed state key
was created or changed only inside the removed sessions, was absent from the
authenticated checkpoint that started the quarter, and is not changed by any
retained quarter session. Partial-thread removal is always rejected. The local
replay omits removed sessions, including their app operations and temporary
state records.

The runner copies saved planner and writer records as accepted source-generation
provenance, applies the approved corrections to saved `plan.json` files, renders
the retained sessions, and deterministically replays app operations from the
configured starting checkpoint. It rebuilds checkpoint state and the complete
candidate chain locally using the normal history-window state helpers. The
saved weekly calls remain recorded as source generation and are not counted as
new paid calls. The correction run makes exactly one fresh whole-quarter review
call. It writes `final_checkpoint` only when that review passes.

During this local correction replay, each retained operation keeps the exact
saved replay time from the failed source window, identified by its session ID
and its operation number within that session. This preserves generated record
IDs when an unrelated earlier operation is removed. A replacement operation at
an existing position keeps that position's saved replay time. If an approved
replacement adds an operation after the source session's original operations,
the runner assigns a new unused replay time at that session's narrative time,
after the session's earlier operations. It never reuses a time from the source
or another corrected operation. A retained operation that refers to a record
created only by a removed operation still fails locally; the correction cannot
keep a dependency whose record is no longer present.

## What Counts As An Input

For a new quarter, the active inputs are:

- the persona spec, persona sheet, generator context, and overview;
- the previous accepted quarter plan;
- the accepted starting checkpoint; and
- the newly accepted quarter plan and its config.

When an older previous-plan file contains retired fields, the planner reads
only the five fields above. The old file remains available for provenance, but
its weekly data is not an active input.

A checkpoint contains the accepted history, session purposes, entities, facts,
simulated app state, and operation results. Each new weekly checkpoint is
authenticated before it becomes the next week's input.

Only a checkpoint under a `*_final` quarter directory may start a new quarter.
`*_current` directories, candidate runs, failed runs, and provenance receipts
are not executable starting points.

## Historical Files That Are Not Active Inputs

Old schedules, rewrite trees, one-off repair tools, and state-timeline builders
are historical provenance kept outside this checkout. They are not part of the
current pipeline and must not be used to plan or execute a new quarter.

`construction.prepare_initial_history` is the local-only preparation boundary
for repairing Alex's or Riley's original short history. Retired seed builders
and validators are not included. They are not quarter-generation commands.

The initial Alex/Riley preparation order is:

1. Treat the original messages and registry as the immutable source.
2. Write one request. Its response includes every session/message pair in
   `messages_checked`, so deterministic code can reject skipped messages.
   `problems` contains only messages needing repair; later-
   outcome narration is a repair problem, but real plans and deadlines are not.
3. Have a human accept the problem list.
4. Write one request that rewrites only the messages whose problems were
   accepted.
5. Deterministic code applies only those accepted replacements to the repaired
   `life_sim.yaml`.
6. Have a human review the resulting changes.
7. Build the entity inventory, protected-fact subjects, and chronological
   missing-fact list from the repaired messages.
8. After a human accepts the missing facts, write one saved app-effects
   request. It classifies every repaired message as needing an incoming
   record, reporting an already-completed app change, requesting an available
   app action, or making an unsupported external request. It contains every
   manifest-listed simulated tool and its exact server argument signature,
   with contract metadata when available. It does not create records, choose
   tool arguments, replay actions, or create a checkpoint. Stop for human
   acceptance of that request and its response.
9. Leave dates, simulated app state, record construction, action replay, and
   the candidate checkpoint for later work.
10. Treat the run 002 entity response as diagnostic provenance only, never as
   active input.
11. Make no paid call and write no next request without explicit human
   approval.

`initial_history_repair_003` predates the `messages_checked` coverage field and
was completed by an explicit local audit that amended the accepted list.

The original source files remain immutable. If a complete-history review finds
a demonstrably false message or fact statement, a human may approve an exact
text correction in the run's `corrections/approved_text_corrections.json`.
Code verifies the prior text exactly before applying it. A fact correction may
change only the statement; its ID, scope, source sessions, related sessions,
and all other fields remain protected. These corrections are part of the
repaired run, not edits to the source registry.

If the accepted entity review finds exact inventory errors, the run may also
contain `corrections/approved_entity_inventory_corrections.json`. That record
may correct first-appearance session IDs, remove unsupported aliases, replace
an incorrectly merged entity, or add a demonstrated missing entity. Code
checks every referenced prior value, verifies that retained aliases occur in
the supplied history or facts, and rejects an introduction that follows an
exact alias occurrence. The paid response remains unchanged as provenance.

If the accepted protected-fact subject mapping contains exact subject errors,
the run may also contain
`corrections/approved_fact_subject_corrections.json`. This optional overlay
must name the raw response as `responses/existing_fact_subjects.json`, record
the exact original subject list for each corrected numeric fact ID, and replace
it with a non-empty list of accepted entity IDs. Code checks the version,
persona, source response, fact IDs, original list order, replacement entities,
duplicate IDs, and reason before applying it. The raw response is not changed;
the corrected mapping is used for every later protected-fact input and
checkpoint construction.

Local preparation makes no model calls. The request executor runs only an
explicitly named, human-approved saved request. Initial preparation does not
assemble a complete candidate checkpoint.

Provenance directories and run receipts record what happened. They are not
executable plans or checkpoints.

## Final Release Cutoff

Quarter construction may continue past a corpus's published token target so
the last generated week or quarter remains complete. After construction is
accepted, `construction.finalize_token_budget` creates the published corpus at
the first complete session at or above the requested `o200k_base` user-message
token count. It makes no model calls. It deterministically replays the retained
app operations, removes later sessions and records derived from them, and
writes a separately authenticated release checkpoint.

The release checkpoint is the only input to fact selection and test authoring.
The longer source-quarter checkpoint remains construction provenance. A
release checkpoint is not a valid starting point for another quarter;
quarter generation still starts only from an accepted `*_final` quarter
checkpoint.

## Short Rule

To extend a persona: create and human-accept one quarter plan, write one
accepted config, then run `construction.quarter_runner` from the previous
`*_final` checkpoint. No other construction path is canonical.
